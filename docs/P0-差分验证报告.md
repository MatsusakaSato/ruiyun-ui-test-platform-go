## 2. xlsx 层：发现并修复的 3 个缺陷

### 2.1 🔴 关键词补全分支不互斥（确定性错误，影响面最大）

**现象**：item[82] —— Go 推 `['ppt','excel']`，Python 只推 `['ppt']`。

**根因**：Python 原版第 4 步是 **`if/elif` 互斥链**（只补一个目标）；Go 移植写成了**顺序 `if`**，同一句命中多个关键词时会同时补出多个。

该 item 的提问是「…实验探究**课件**，含实验电路图、数据记录**表格**、结论分析。」—— 同时含「课件」(ppt) 与「表格」(excel)，Python 停在 ppt，Go 两个都加。

**影响**：目标集合决定「期望交付哪种产物」，会传导到断言、覆盖率与评分 —— 属于**会改变测试结论**的缺陷。

**修复**：`internal/xlsx/xlsx.go` 改回互斥链，抽出 `hitKey()`。

### 2.2 🟠 nil slice 被序列化成 `null`（前端契约破坏）

**现象**：`attachments` **1000/1000** 项、`expect_tools` **858/1000** 项不一致 —— Go 给 `null`，Python 给 `[]`。

**根因**：Go `var s []string` 是 nil → `encoding/json` 输出 `null`；Python 列表推导天然产出 `[]`。

**影响**：前端做防御式读取（`?? []`、`!= null`）。`null` 与 `[]` 在 JS 中**不等价**，会导致 `length`、`for...of`、`.map` 静默异常。

**修复**：`items` / `attachments` / `expectTools` / `targets` 全部初始化为空切片。

### 2.3 🟡 map 遍历导致输出不可复现

**现象**：同一输入 30 次运行出现 **3 种结果**：

```
22× ('ppt','word') ('ppt','excel') ('ppt','html')
 6× ('ppt','word') ('ppt','excel') ('html','ppt')   ← item97 顺序翻转
 2× ('word','ppt') ('ppt','excel') ('ppt','html')   ← item68 顺序翻转
```

**根因**：`for k := range kinds` —— Go 的 map 迭代顺序**故意随机化**。

**影响**：测试结果抖动、归档不可复现、差分验证永远无法收敛。

**修复**：显式 `kindOrder` 固定遍历顺序。修复后 10 次运行 MD5 完全一致。

## 3. DB 层：发现并修复的 3 个缺陷

### 3.1 🔴 多选目标是「且」而非「或」（用户可见的错误结果）

**现象**：真实库上 `targets=['word','ppt']` —— Go 返回 **7** 条，Python 返回 **863** 条。

**根因**：

```python
# Python：单条 EXISTS + IN → 或语义
EXISTS (SELECT 1 FROM json_each(testcases.targets) WHERE value IN (?,?))
```
```go
// Go（修复前）：每个目标一条 EXISTS，再用 AND 串起来 → 且语义
EXISTS (... WHERE value = ?) AND EXISTS (... WHERE value = ?)
```

**影响**：用例库的多选目标筛选是「命中任意一个」。Go 版会让用户看到远少于预期的结果 —— 这是**用户可感知的功能错误**。

**修复**：改为单条 `EXISTS ... WHERE value IN (...)`。

### 3.2 🔴 `limit` 钳制规则不符（分页失控 + 边界错误）

**现象**（真实库实测）：

| 输入 limit | Python | Go（修复前） |
|---|---|---|
| 501 | 500 | **501** |
| 1000 | 500 | **1000** |
| -5 | **1** | **50** |

**根因**：Python 是 `max(1, min(int(limit or 50), 500))`；Go 只写了 `if limit <= 0 { limit = 50 }` —— **既缺 500 上限**，又把负数错误回落成 50（Python 里负数仍是真值，不触发 `or 50`，而是被 `max(1,·)` 钳到 1）。

**影响**：`limit=1000` 会一次性拉回全库，前端分页与性能均受影响。

**修复**：按 `max(1, min(limit or 50, 500))` 的语义显式实现三段钳制。

### 3.3 🟡 附件筛选接受了 Python 不认的取值

**现象**：Python 只认字面量 `"yes"` / `"no"`（不 trim、不小写）；Go 额外接受 `"1"` / `"true"` / `"0"` / `"false"`。

**影响**：同一请求在两侧得到不同结果。前端目前只发 `''/yes/no`，因此**当前不可达** —— 但属于契约偏离，改为严格对齐。

## 4. ⚠️ 重要发现：Python oracle 自身是不确定的

这是本次验证最重要的架构性结论，**直接影响后续所有差分验证策略**。

### 4.1 证据

`infer_targets`（`core/xlsx_reader.py:264`）内部：

```python
kinds, _ = infer_target_kinds(prompt)   # 返回 set
for k in kinds:                          # ← 遍历 set
    ...
    targets.append(mapped)
```

`kinds` 是 **set**，Python 对 str 的哈希默认随机化（`PYTHONHASHSEED`），因此**同一输入、同一份代码，多次运行会得到不同顺序的 `targets`**。

实测：Python 侧连续 12 次运行 → **4 种不同结果**：

```
4× ('word','ppt') ('html','ppt')
4× ('ppt','word') ('ppt','html')
2× ('word','ppt') ('ppt','html')
2× ('ppt','word') ('html','ppt')
```

### 4.2 这意味着什么

1. **「逐字节对齐 Python」这个验收目标本身不成立** —— oracle 自己都不确定。
2. 严格 diff 会持续报出「幽灵差异」，误导移植者去"修"一个并不存在的 Go 缺陷。
3. §2.3 里 Go 的不确定性，其实是**忠实继承了 Python 的缺陷**，而非新引入。

### 4.3 建议（需要项目级决策）

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 两侧都改确定性**（推荐） | Go 已改（`kindOrder`）；Python 侧把 `for k in kinds` 改为按固定顺序遍历 | 根治。但**改 Python 原版需用户明确授权**（本次已按要求未改动） |
| B. 差分时归一化顺序 | 即本工装当前做法 | 可行，但掩盖真实顺序契约 |
| C. 不处理 | 接受抖动 | ❌ 不可接受：归档不可复现 |

> 📌 **待你决策**：是否同步修改 Python 原版 `infer_targets`（约 1 行）。未改之前，`targets` **顺序不能作为验收契约**。

## 5. 剩余已知偏离（无害，但需知晓）

Go 的 `rowToCase` 输出比 Python `_row_to_case` **多两个顶层键**：

```
Python 键集: attachments, expect_tools, id, labels, name, prompt
Go     键集: attachments, expect_tools, id, labels, name, prompt, scene, targets
```

**已确认无害**：前端读的是 `c.labels.scene` / `c.labels.targets`（`web/js/page-cases.js:203-204`），并**不读** `c.scene` / `c.targets`；Go 内部也没有消费者（其余代码都读 `labels[...]`）。

**处理**：差分工装默认忽略这两个键。若你希望与 oracle 达到**严格字节一致**，删掉 `internal/testcasedb/testcasedb.go` 中 `rowToCase` 的这两行即可（我未擅自删除，因为它是设计选择而非缺陷）。
