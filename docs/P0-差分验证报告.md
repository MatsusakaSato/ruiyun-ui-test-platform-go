## 1. 差分工装

| 文件 | 作用 |
|---|---|
| `cmd/tracediff/main.go` · `tools/diff/trace_ref.py` · `tools/diff/run_trace_diff.py` | **分析层**探针 / Python 参照 / 运行器 |
| `cmd/xlsxdiff/main.go` · `tools/diff/xlsx_ref.py` · `tools/diff/run_diff.py` | xlsx 层 |
| `cmd/dbdiff/main.go` · `tools/diff/db_ref.py` · `tools/diff/run_db_diff.py` | DB 层（**只读**） |
| `cmd/metricsdiff/main.go` · `tools/diff/metrics_ref.py` · `tools/diff/run_metrics_diff.py` | **指标层**（trajectory + metrics） |
| `cmd/evaldiff/main.go` · `tools/diff/eval_ref.py` · `tools/diff/run_eval_diff.py` | **评估前置层**（formatcheck + safetyscan + intent） |

**设计要点**
- Python 侧一律 import 原版实现，比对的是真实生产行为，而非"我理解的 Python 行为"；
- 自动定位原项目 `.venv`；构建产物落在临时目录，不污染源码树；
- 退出码 0/1，可直接接 CI 作门禁；
- DB 层给两侧**各一份独立副本**，绝不写生产库；
- 正文/结果只输出**哈希 + 码点长度** —— 长度相等不代表内容相等，必须用哈希才能证明；
  码点长度则专门用来暴露 `len(str)` vs `len(string)` 的差异。
- **指标层不比哈希**：Go 与 Python 的浮点序列化不同（Go `100` / Python `100.0`），
  跨语言哈希必然不等。改为把两侧结构拉回来做**递归结构化比较**，数值按数值比、按 JSON 路径报差异。
- **键序类差异要用「交叉校验」证明**：`args_summary` 是 `json.dumps(arguments)` 的**截断**展示，
  截断后无法归一化。故两侧探针**额外输出未截断、键已排序的 `args_canon`**；
  只有它完全相等，才把 `args_summary` 的差异归为"纯键序"。**这是证明，不是豁免。**
- **语料 = 真实数据 + 对抗注入**（本轮新增的做法）：真实语料保证覆盖面，
  对抗注入保证**已知陷阱一定会被踩到**。`run_eval_diff.py` 除 219 个真实会话外，
  还给每个会话生成 2 个变体（在要求项 / 安全源文本里塞 Unicode 空白），
  外加 **10 个逐字符的纯对抗用例**（Python `\s` 独有的 10 个字符各一个）。
  理由：真实语料里 U+2028 只出现 **1 次**、U+2003 出现 64 次 —— 靠真实数据覆盖是碰运气。
  本轮最有价值的两个发现（U+2028 转义、U+001C strip）**都是对抗注入先炸出来的**。

## 2. xlsx 层：3 处缺陷

### 2.1 🔴 关键词补全分支不互斥

**现象**：item[82] —— Go 推 `['ppt','excel']`，Python 只推 `['ppt']`。

**根因**：Python 第 4 步是 **`if/elif` 互斥链**（只补一个目标）；Go 写成了**顺序 `if`**。
该提问「…实验探究**课件**，含实验电路图、数据记录**表格**、结论分析。」同时含
「课件」(ppt) 与「表格」(excel)，Python 停在 ppt，Go 两个都加。

**影响**：目标集合决定期望交付哪种产物，会传导到断言、覆盖率与评分 —— **会改变测试结论**。

### 2.2 🟠 nil slice 被序列化成 `null`

**现象**：`attachments` **1000/1000** 项、`expect_tools` **858/1000** 项不一致。

**根因**：Go `var s []string` 是 nil → `encoding/json` 输出 `null`；Python 产出 `[]`。

**影响**：前端做 `?? []` 防御式读取，`null` 与 `[]` 在 JS 中**不等价**。

### 2.3 🟡 map 遍历导致输出不可复现

**现象**：同一输入 30 次运行出现 **3 种结果**（item 顺序在 68/97 翻转）。

**根因**：`for k := range kinds` —— Go map 迭代顺序**故意随机化**。

**影响**：结果抖动、归档不可复现、差分永远无法收敛。修复后 10 次运行 MD5 完全一致。

## 3. DB 层：3 处缺陷

### 3.1 🔴 多选目标是「且」而非「或」

**现象**：真实库 `targets=['word','ppt']` —— Go 返回 **7** 条，Python 返回 **863** 条。

**根因**：Python 是单条 `EXISTS (... WHERE value IN (?,?))`（或语义）；
Go 给每个目标生成一条 `EXISTS` 再用 `AND` 串起来（且语义）。

**影响**：用例库多选筛选是「命中任意一个」。**用户可感知的功能错误**。

### 3.2 🔴 `limit` 钳制规则不符

| 输入 | Python | Go（修复前） |
|---|---|---|
| 501 | 500 | **501** |
| 1000 | 500 | **1000** |
| -5 | **1** | **50** |

**根因**：Python 是 `max(1, min(int(limit or 50), 500))`。Go 只写了
`if limit <= 0 { limit = 50 }` —— **既缺 500 上限**，又把负数错误回落成 50
（Python 里负数仍是真值，不触发 `or 50`，而是被 `max(1,·)` 钳到 1）。

**影响**：`limit=1000` 会一次性拉回全库。

### 3.3 🟡 附件筛选接受了 Python 不认的取值

Python 只认字面量 `"yes"` / `"no"`（不 trim、不小写）；Go 额外接受
`"1"/"true"/"0"/"false"`。前端只发 `''/yes/no`，故**当前不可达**，但属契约偏离。

## 4. 分析层：14 处缺陷（本轮新增）

语料：**219 份真实会话、1037 次工具调用**。修复前 **8 个顶层字段 + 4 个调用级字段**
大面积不一致；修复后全绿。

### 4.1 🔴 `session.meta.json` 键名读错（P0，影响 219/219）

`session.meta.json` 实际用 **snake_case**：

```json
{"session_id": "sess_...", "created_at": "2026-09-14T14:23:12.166515",
 "updated_at": "2026-09-14T14:26:14.789526", "title": "...", "status": "active"}
```

Go 读的是 `meta["id"]` / `meta["createdAt"]` / `meta["updatedAt"]`，
而取值又走 `fmt.Sprintf("%v", nil)` —— 于是三个字段**全部变成字面量字符串 `"<nil>"`**。
`session_id` 是 UI 主键，属 P0。

> ⚠️ 这条同时暴露了一个通用陷阱：**`fmt.Sprintf("%v", nil)` 会产出字符串 `"<nil>"`**，
> 而不是空串。已引入 `pyStr()`（复刻 Python `d.get(k, "")`）统一处理。

**附带**：`session_id` 还需按 Python 规则回退到**目录名**
（`meta.get("session_id") or session_dir.name`）。

### 4.2 🔴 步骤序号全量偏移 +1（1037/1037 处）

Python 的 `step_index` 是「**先取当前值，循环末尾再 `+1`**」，首个步骤 index=0，
且**跨 assistant 消息连续累加**。Go 写成先 `++` 再取 → 全部 `index` 偏移 +1，
并连带污染 `message_spans` 的 `first_step` / `last_step`。

### 4.3 其余 12 处

| # | 缺陷 | 说明 |
|---|---|---|
| 3 | `source_file` 语义错 | Python 存**会话目录**，Go 存 messages.json 文件路径 |
| 4 | `event_type` 完全没提取 | 应取结果外壳的 `meta_res.get("event_type","")` |
| 5 | `session_id` 未回退 | `meta_res.get("session_id","") or trace.session_id` |
| 6 | `request_id` 未回退 | `meta_res.get("request_id","") or msg.get("request_id","")` |
| 7 | `turn_prompt` 多轮取错 | Python 每条 user 消息刷新触发源；Go 永远记首条提问 |
| 8 | 派生耗时未取整 | Python 是 `round(x,2)`（如 2.421342 → 2.42） |
| 9 | 缺 `generation_s` 兜底分支 | Python 有 `elif t_user and t_done` |
| 10 | `message_spans` 无条件记录 | Python 只在 `span_last >= span_first` 时记录（17 会话受影响） |
| 11 | `reasoning_chars` 来源错 | Python 用整条消息的 `reasoningContent`，非 thinking 步骤之和 |
| 12 | `final_answer` 跳过空串 | Python 取最后一条 `content is not None`，**空串也算** |
| 13 | `empty_required_arg` nil→`null` | Python 返回 `[]`（1037 次调用全部不一致） |
| 14 | `Signature()` 格式不符 | 见 4.4 |

### 4.4 🔴 `Signature()` 格式 —— 比看起来重要得多

`core/trajectory.py:68,86` 会取签名的**长度**参与 `tool_arg_chars` 与 token 估算，
所以格式差异会**直接污染指标**，不是洁癖问题。

| | Python `json.dumps(args, ensure_ascii=False, sort_keys=True)` | Go `json.Marshal` |
|---|---|---|
| 分隔符 | `{"a": 1, "b": 2}`（**有空格**） | `{"a":1,"b":2}` |
| HTML | 不转义 `< > &` | 转义为 `\u003c` 等 |
| 整数 | `8` | float64 形态不定 |

→ 已实现 `PyJSONDumps()` 逐字节复刻。

**关于整数**：Python 只对 `json.loads` 得到的 `int` 输出无小数点形态；Go 统一解码成
`float64`，故把「整数值」还原为整数形态。真实语料实测：

```
int 字面量       : 3626
非整数 float     : 52
整数值 float     : 0     ← 关键：0 个
```

因此该还原在本语料上**完全精确**。

> ⚠️ **残留边界**：若出现 `8.0` 这类字面量（Python 保 float → 输出 `"8.0"`），
> 或超出 2^53 的大整数，仍会不一致。彻底解决需在解码侧改用 `json.Number`。
> 当前判断：不值得为此改动解码路径（会波及 evaluator 等处对 `.(float64)` 的断言）。

## 5. 断言层：5 处缺陷（本轮新增）

语料：与 §4 **完全相同**的 219 会话，产出 **229 条 Finding**，覆盖 **9 类规则**
（`TOOL_CALL_FAILED` 105、`NO_FINAL_ANSWER` 30、`LOOP_CONSECUTIVE` 26、
`LOOP_TOTAL` 20、`DUPLICATE_CALL` 17、`SESSION_NOT_CLOSED` 11、
`TOOL_RESULT_MISSING` 11、`EMPTY_REQUIRED_ARG` 6、`OUTPUT_TRUNCATED` 3）。

**修复前 37 条 finding 不一致，修复后 0 条。**

### 5.1 🔴 `LOOP_TOTAL` / `DUPLICATE_CALL` 的 finding 顺序随机（16 条）

| | Python | Go（修复前） |
|---|---|---|
| `LOOP_TOTAL` | `Counter`（dict 子类）→ **首次出现顺序** | `for nm, c := range counts` → **随机** |
| `DUPLICATE_CALL` | `seen.setdefault(...)` 的 dict → **首次出现顺序** | `for k, items := range seen` → **随机** |

**与 §2.3 同源的一类缺陷**：Go map 迭代顺序被故意随机化，而 Python 的 dict
自 3.7 起保证插入有序。后果是**同一输入每次运行产出顺序不同的 Finding 列表** ——
归档不可复现、报告 diff 永远无法收敛。

> 判据不是"看起来对"，而是"跑 20 次顺序完全一致"（已写入回归测试）。

### 5.2 🔴 `error_markers` 没有小写（12 条）

Python：`markers = [m.lower() for m in cfg.get("error_markers", [])]`。

生产配置里**同时存在** `"[ERROR]"` 与 `"[error]"` 两个条目。Go 侧没有小写，
于是它们被当成**两个不同特征**，同一次命中会在 detail 里同时列出：

```
Go : 调用失败（命中特征：[ERROR], [error], failed to, ...）
Py : 调用失败（命中特征：[error], failed to, ...）
```

隐蔽之处：`matchMarker()` 内部**本来就会小写**，所以**匹配行为完全正确**，
错的只是**记录下来的命中列表** —— 纯看代码很难发现，只有差分能暴露。

### 5.3 `OUTPUT_TRUNCATED` 的结尾摘录没做 repr 转义（3 条）

Python 写的是 `实际结尾：…{body[-60:]!r}` —— 这里 `!r` 是 **`repr()`**。
于是答案里的换行会输出成**字面量 `\n`**（反斜杠 + n），
而 Go 直接用 `'%s'` 输出原始切片 → 真实换行。

凡是含换行的最终答案都会不一致。已实现 `pyRepr()` 复刻 Python `repr(str)`：
单引号优先、含 `'` 而无 `"` 时改用双引号、转义 `\ \n \r \t`、
**非 ASCII 可打印字符原样保留**（Python 3 的 repr 不做 ASCII 转义）。

### 5.4 `OUTPUT_TRUNCATED` detail 多一个空格（3 条）

Python 是 `f"...字）。" + " ".join(...)` —— 单个信号时 `。` 后**没有**空格；
Go 写成 `"。 %s"`，凭空多一个空格。

### 5.5 已知显示层差异：`EMPTY_REQUIRED_ARG` 的 evidence 键序（6 条）

Python：`json.dumps(t.arguments, ensure_ascii=False)` —— **注意没有 `sort_keys`**，
所以保留的是 **JSON 源文件里的键序**；Go 的 `map[string]any` **不保留键序**。

```python
# Python（源文件键序）
{"md_file_name": "李白生平详细介绍.md", "markdown_content": ""}
# Go（键排序）
{"markdown_content": "", "md_file_name": "李白生平详细介绍.md"}
```

**未修的理由**：彻底解决要在**解码侧**保留键序，会波及所有
`Arguments.(map[string]any)` 类型断言与 `PyJSONDumps` —— 为了 6 个**纯展示字符串**
的键序去动已经验证通过的 logparser，**风险大于收益**。

**门禁的处理**：`run_assert_diff.py` 会把两侧 evidence 归一化成
「键排序后的紧凑 JSON」**再比一次**；**只有归一化后完全相等**才归入这一已知类别。
这不是"放过"，而是"证明唯一差异就是键序" —— 内容若有任何实质不同，仍然报错。

## 6. 指标层：15 处缺陷（本轮新增）

指标层是把**前四层的输出**再加工成界面事实载荷与归档：
`parse_session → run_assertions → build_case_detail → build_round_detail → build_metrics`。
正因为它是**下游的下游**，上游每一处偏差都会在这里放大 ——
本轮差分**起始状态是 219/219 个用例的 detail 全部不一致**，
聚合 metrics 有 1124 处差异。逐步收敛到 0。

### 6.1 🔴 `sessions_closed` 算错（219 vs 188）

`core/metrics.py` 数的是**客观标记**：

```python
sessions_closed = sum(1 for o in all_obj if o["status"]["session_closed"])
```

Go 写成了 `len(caseResults) - len(uiFailed)` —— 一个**看似合理但完全不同**的代理指标。
219 个用例里差出 31 个。这类"用相近的量替代"是移植中最危险的错误：
它不会崩，只会安静地给出一个错的数。

### 6.2 🔴 银行家舍入：`round(31.25, 1)` Python 给 31.2、Go 给 31.3

Python 的 `round()` 是 **half-to-even**，Go 的 `math.Round` 是 **half-away-from-zero**。
真实语料里 error_rate 恰好命中了 `.xx5`：

| 值 | Python `round(x,1)` | Go `math.Round(x*10)/10` |
|---|---|---|
| 31.25 | **31.2** | 31.3 |
| 2.675（2 位） | **2.67** | 2.68 |
| −31.25 | **−31.2** | −31.3 |

已实现 `trajectory.PyRound(x, nd)`：基于 `math/big.Rat` 取浮点数的**二进制精确值**，
再做 ties-to-even —— 不是"加 0.5 再截断"那种近似写法。
`RoundToOneDecimal` 与 `metrics.pct` 均已转调它。

> ⚠️ 这条**推翻了此前"当前语料无差异"的结论**。之前只测了会话耗时（没有恰好半值），
> 没测到比率字段。**教训：`round()` 的差异要用真实语料穷举，不能靠抽样印象。**

### 6.3 🔴 四处 `sort.Slice` 该用稳定排序（顺序随机）

Python 的 `list.sort()` / `sorted()` **稳定**，并列元素保持原顺序；
Go 的 `sort.Slice` **不稳定**。指标层四处中招：

| 位置 | Python 的稳定来源 | 现象 |
|---|---|---|
| 步骤时间线 `merged` | 先入列全部 tool call，再入列 thinking → 下标相同时 tool 在前 | 87 处 `i` / 61 处 `type` 漂移 |
| `tools` / `round_tools` | `Counter.most_common()` 并列保持首次出现序 | 同调用次数时顺序随机 |
| `rule_rows` | `RULES.items()` 声明序 | **双重随机**（map 遍历 + 不稳定排序） |
| `findings_rows` | `sorted(findings, key=...)` | 同优先级时顺序随机 |

全部改为 `sort.SliceStable`；`tool_rows` / `rule_rows` 另外显式记录
**首次出现序**（`toolOrder`）与**规则声明序**（`assertor.RuleOrder`），

### 7.1 总根因：Python 的 `\s` 不是 Go 的 `\s`（新建 `internal/pyre`）

Python `re` 对 str 模式的 `\s` == `str.isspace()` 集合，**29 个码点**；
Go `regexp` 的 `\s` == `[\t\n\f\r ]`，只有 **5 个**。

由 Python 实测生成权威集合：

```python
python3 -c "import re;print([hex(c) for c in range(0x110000) if re.match(r'\\s',chr(c))])"
# 29 个：U+0009-000D, U+001C-001F, U+0020, U+0085, U+00A0, U+1680,
#        U+2000-200A, U+2028, U+2029, U+202F, U+205F, U+3000
```

**推导**：Python 的 `\s` 集合 == Go `unicode.IsSpace` 的集合（25 个）
**加上** U+001C–U+001F（ASCII 文件/组分隔符/记录分隔符/单元分隔符）。

差异集合里有 4 个在中文语料里**极常见**（219 份会话实测）：

| 字符 | 出现次数 | 场景 |
|---|---|---|
| U+2003 EM SPACE | **64** | 排版空格 |
| U+3000 全角空格 | **21** | 中文排版 |
| U+000B 垂直制表 | **19** | 复制粘贴带出 |
| U+2028 行分隔符 | **1** | 同上 |

**42. 🔴 `formatcheck` 的 `reSplit` / `rePunct` 直接用了 Go 的 `\s`。**
`_norm()` 归一化时 Python 会把 `"包含　页眉"`（全角空格）变成 `"包含页眉"`，Go 不变
→ **要求项覆盖率静默算错**。


**48. 🔴 `safetyscan` 的规则正则同样用了 Go 的 `\s`。**
`rm\s+-[A-Za-z]*[rf][A-Za-z]*\s+(?:/|~|\$HOME|\*)` 等。
后果比 42 更严重 —— 见 §7.3 第 50 条。

## 8. ⚠️ 重要发现：Python oracle 自身有两处缺陷

本节两条都**不是 Go 的缺陷**，而是 oracle 自身的问题 —— 但性质完全不同：
`8.1` 是**不确定**（无法逐字节对齐），`8.2` 是**确定的功能缺失**（可以对齐"修好之后"的语义）。

### 8.1 oracle 的不确定性：`infer_targets` 遍历 set

这是本次验证最重要的架构性结论，**直接影响所有差分验证策略**。

`infer_targets`（`core/xlsx_reader.py:264`）遍历的是 **set**，Python 对 str 的哈希默认
随机化（`PYTHONHASHSEED`），因此**同一输入、同一份代码，多次运行会得到不同顺序的
`targets`**。实测 Python 侧连续 12 次运行 → **4 种不同结果**。

**含义**：
1. **「逐字节对齐 Python」这个验收目标本身不成立** —— oracle 自己都不确定；
2. 严格 diff 会持续报出**误导性的"幽灵差异"**，诱导移植者去"修"一个并不存在的缺陷；
3. Go 侧的不确定性其实是**忠实继承了 Python 的缺陷**，而非新引入。

**建议**：Go 侧已确定化（优于 Python）；Python 侧把 `for k in kinds` 改为固定顺序
（约 1 行）即可根治，但**改 Python 原版需用户明确授权**（本次已按要求未改动）。

> 📌 **待决策**：是否同步修改 Python 原版 `infer_targets`。
> 未改之前，`targets` **顺序不能作为验收契约**。

### 8.2 🐞 oracle 的第二个缺陷：`issues` 恒为空（确定性，非随机）

与上面的"随机顺序"不同，这是**确定的、100% 复现的功能缺失**。

`core/trajectory.py:401`：

```python
"issues": sorted({f.rule for f in findings_by_step.get(tc.index, [])}),
```

唯一调用方（同文件 `:506-508`）构造的字典，key 是 **(session_id, step_index) 元组**：

```python
by_step.setdefault((c.session_id, f.step_index), []).append(f)
...
_step_dict(tc, findings_by_step, ...)
```

用 `tc.index`（一个 int）去查元组键，**永远查不中** → **`issues` 恒为 `[]`**。

**佐证这几乎肯定是笔误**：同文件 `:141` 的 `_step_status` 用的是正确形态
`findings_by_step.get((session_id, tc.index))`，而且它的 docstring **专门警示过**：

> findings_by_step 的 key 是 `(session_id, step_index)` 元组 —— 必须用同样形态查。

**影响**：详情页每个工具步骤的「问题」徽标**从来没显示过**。

**本次处理**：Go 按**正确语义**实现（复合键），即 Go 的输出是 Python **修好之后**的样子。
差分器把这类差异单列为 `oracle缺陷` 桶（判据：Python 为 `[]` 且 Go 为已排序非空列表），
**不计入真实差异，但每次运行都打印计数** —— 不掩盖。

> 📌 **待决策**：是否修 Python 这一行（1 行）。
> 修复后 `issues` 会从恒空变成有值，属**行为变更**，需评估对历史归档的影响。

## 9. 剩余已知偏离（无害但需知晓）

### 9.1 `rowToCase` 多两个顶层键

Go 的 `rowToCase` 输出比 Python `_row_to_case` **多两个顶层键**：

```
Python: attachments, expect_tools, id, labels, name, prompt
Go    : attachments, expect_tools, id, labels, name, prompt, scene, targets
```

**已确认无害**：前端读的是 `c.labels.scene` / `c.labels.targets`
（`web/js/page-cases.js:203-204`），**不读** `c.scene` / `c.targets`；Go 内部也无消费者。

**处理**：DB 差分工装默认忽略这两个键。若要严格字节一致，删掉 `rowToCase` 中那两行即可
（未擅自删除，因为这是设计选择而非缺陷）。

### 9.2 键序差异（187 处指标层 + 6 处断言层 + 282 处评估前置层）

Python 的 `json.dumps` **不传 `sort_keys`** 时保留的是**源文件里的键序**；
Go 的 `map[string]any` **不保留键序**，只能有序输出。

```python
# Python（源文件键序）
{"md_file_name": "李白生平详细介绍.md", "markdown_content": ""}
# Go（键排序）
{"markdown_content": "", "md_file_name": "李白生平详细介绍.md"}
```

**为什么没修**：彻底解决要在**解码侧**保留键序（自定义 decoder 或有序容器），
会波及所有 `Arguments.(map[string]any)` 类型断言与 `PyJSONDumps`。
为了**纯展示字符串**的键序去动已验证通过的 logparser，**风险大于收益**。

**处理方式（这是证明，不是豁免）**：指标层差分器让两侧探针**额外输出
未截断、键已排序的 `args_canon` 规范形**；只有它完全一致，
才把 `args_summary` 的差异归入此类。本次实测 `args_canon` **✅ 完全一致**，
故 187 处全部坐实为纯键序。

**评估前置层同理**：`safetyscan` 的 `sources` 里 282 处差异，
全部是工具实参 JSON 对象的键序（如 `{"query": …, "max_results": …}` vs 排序后）。
`run_eval_diff.py` 对两侧 `sources` 的值做「解析 → 键排序 → 重新 dump」归一化后**再比一次**，
归一化后差异 **0 条** —— 坐实为纯键序。

**另外已实证「键序不影响安全判定」**：`hits` / `redlines` / `has_redline` 的比对
是**不归一化**的（真刀真枪比）—— 归一化前就只有 282 处 `sources` 差异，
`hits` 相关字段**零差异**。原因是所有规则都锚定在单个 `key: value` 对上，
不跨键匹配，因此键序重排不改变任何规则的匹配结果。

### 9.3 `PyJSONDumpsSourceOrder` 对 map 仍会排序

`json.dumps(v, ensure_ascii=False)`（不带 `sort_keys`）在 Python 侧保留**源文件键序**；
Go 侧即使调用 `PyJSONDumpsSourceOrder` 也**只能排序** ——
因为 `map[string]any` 本身不保留键序，不排会导致输出每次运行都不同。

这不是新增缺陷，而是 9.2 那个根因在评估前置层的体现。已在函数文档注释里写明。
